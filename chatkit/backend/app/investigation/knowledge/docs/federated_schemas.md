# Federated Schemas Reference

Production MySQL databases are federated into the Redshift analytics and core clusters as **external schemas**. These are **live production data** — not dev copies — and are Redshift-queryable (JOIN-friendly with other Redshift tables).

> **Key distinction:** `federated_*` schemas (no `local.` prefix) = **prod data**.
> `local.federated_*` schemas = dev-environment-only data used by `ds-priceeye-data-collection`.

---

## Availability by Cluster

| Schema | analytics cluster | core cluster |
|--------|:-----------------:|:------------:|
| `federated_priceeye` | ✓ | ✓ |
| `federated_metadata` | ✓ | ✓ |
| `federated_analytics` | ✓ | — |
| `federated_replication` | ✓ | — |
| `federated_sales_poc` | ✓ | ✓ |
| `federated_scheduling` | — | ✓ |

Routing: `federated_scheduling.*` → `redshift_core`; all other `federated_*` → `redshift_analytics` (default fallback).

## federated_priceeye (analytics + core)

**Mirrors:** MySQL `priceeye` schema (production)

**Purpose:** Customer and site configuration data. Use for lookups of what customers are configured for, which sites/providers they collect from, error classifications, and customer defaults.

**Known tables:**

| Table | Description |
|-------|-------------|
| `federated_priceeye.site_hierarchy` | Customer site configuration — sites, carriers, markets per customer |
| `federated_priceeye.customer_site_code` | Site code to customer mappings |
| `federated_priceeye.error_mapping` | Error code → human-readable description mappings |
| `federated_priceeye.customer_defaults` | Per-customer analytics config flags (anomaly detection thresholds, etc.) |

**Sample queries:**

```sql
-- What sites is customer AA collecting from?
SELECT * FROM federated_priceeye.site_hierarchy
WHERE customer = 'AA'
ORDER BY sitecode;

-- Look up what an error code means
SELECT * FROM federated_priceeye.error_mapping
WHERE error_code = 'TIMEOUT';
```

**When to use:**
- Customer configuration lookups
- Mapping site codes to customer/carrier context
- Error classification analysis
- Comparing customer config against observed behavior

## federated_metadata (analytics + core)

**Mirrors:** MySQL `metadata` schema (production)

**Purpose:** Reference/lookup tables used across multiple DS processes. Currency conversion, geolocation, and other static metadata.

**Known tables:**

| Table | Description |
|-------|-------------|
| `federated_metadata.currencyexchangerates` | Daily currency exchange rates used by daily-process and channel comparison |
| `federated_metadata.airportlocation_extra` | Airport geolocation (lat/lon, timezone, city, country) |
| `federated_metadata.citylocation_extra` | City geolocation enrichment |

**Sample queries:**

```sql
-- Convert EUR prices to USD for a given date
SELECT base_currency, target_currency, rate
FROM federated_metadata.currencyexchangerates
WHERE target_currency = 'USD' AND rate_date = '2026-01-15';

-- Get airport details
SELECT iata_code, city, country, latitude, longitude
FROM federated_metadata.airportlocation_extra
WHERE iata_code = 'JFK';
```

**When to use:**
- Currency conversion in price analysis
- Airport/city geolocation enrichment
- Any analysis needing timezone or geography context

## federated_scheduling (core only)

**Mirrors:** MySQL `scheduling` schema (production)

**Datasource:** `redshift_core` (only available in core cluster)

**Purpose:** AutoSchedule (AS) system data — what collection schedules are configured per customer and market.

**Known tables:**

| Table | Description |
|-------|-------------|
| `federated_scheduling.as_hourly_collection_plans` | Per-customer, per-market hourly collection plans generated by AutoSchedule |

**Sample queries:**

```sql
-- What is the active collection schedule for customer AA?
SELECT customer, market, scheduled_hour, plan_type, status
FROM federated_scheduling.as_hourly_collection_plans
WHERE customer = 'AA'
ORDER BY market, scheduled_hour;

-- How many markets does each customer have scheduled?
SELECT customer, COUNT(DISTINCT market) AS market_count
FROM federated_scheduling.as_hourly_collection_plans
WHERE status = 'active'
GROUP BY customer
ORDER BY market_count DESC;
```

**When to use:**
- Understanding what AutoSchedule has planned for a customer
- Investigating collection gaps (scheduled but not collected)
- Comparing planned vs. actual collection volume

## federated_analytics (analytics only)

**Mirrors:** MySQL `analytics` schema (production)

**Purpose:** Analytics configuration and reference tables — alert schedules, anomaly weights, carrier groups, cabin groups, segments, etc. These are the MySQL-side configuration tables that govern how the DS analytics pipeline behaves.

**Known tables** (run `_discover_federated_tables()` to get the full live list):

| Table | Description |
|-------|-------------|
| `federated_analytics.alerts_schedule` | When alerts fire per customer/market |
| `federated_analytics.anomalies_direction_score` | Direction scoring weights for anomaly detection |
| `federated_analytics.anomalies_impact_score_weights` | Impact score weights |
| `federated_analytics.cabin_group` | Cabin groupings used in analysis |
| `federated_analytics.carrier_group` | Carrier groupings |
| `federated_analytics.date_range` | Date range definitions |
| `federated_analytics.demo_carrier_substitutions` | Demo mode carrier substitutions |
| `federated_analytics.geography_entry` | Geography groupings |
| `federated_analytics.region` | Region definitions |
| `federated_analytics.segment` | Segment definitions for analysis |

**When to use:**
- Understanding how anomaly scoring is configured
- Checking alert schedules
- Looking up carrier/cabin/geography groupings used in analytics

## Caveats

1. **Read-only:** All federated schemas are read-only. No writes.
2. **Live prod data:** Changes in the MySQL source are reflected immediately (no ETL delay).
3. **No partition filtering needed:** These are small configuration tables — no `sales_date` partition required.
4. **Federation latency:** Occasional latency on first query if federation connections are cold-started. Retry once if a query times out.
5. **`local.federated_*` vs `federated_*`:** The `local.` prefix indicates dev-environment Redshift data. Always use `federated_*` (no prefix) for production data.
